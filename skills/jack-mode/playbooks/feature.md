### Feature

**You own the design. Align, grill, build, verify.** Delegate implementation where it helps. Stay in the lead.

1. Align with the codebase (the **principle-align-with-existing-practices** skill). Run `how` over the affected subsystem and sweep for the task's close relatives (the precedent sweep in the **grilling** skill): sibling features, their tests, and how they were built in `git log`. Read the best-practice skills for every language and framework the feature touches, including the project's own framework skills (see the Non-negotiables in `../SKILL.md`), so the grilling questions and the design already follow them.
2. For anything a user sees, run the **ui-design** skill's research, plan and proposal first, and bring its plan into the grilling. Grill Jack with the **grilling** skill until the design tree is empty: behavior, edge cases, data shape, UX, scope, what is out. Follow the precedent map and make the cheap calls yourself, listed in each round. Ask the judgement calls. Data models and every user-facing surface always go to Jack. Settle factual forks with the Prototype playbook instead of asking. Read and trace the code behind every fact a question states. Ask each design question with the simplest option first, the one where every case works the same way, per **principle-fewest-moving-parts**, and recommend it unless the code rules it out. For a new feature, core logic, or an architecture change, write the spec with **to-spec** (`.jack/specs/<feature>.md`, never committed), and record architecture decisions and new terms with **domain-modeling**.
3. Shape it. Name the data shape and its organizing structure per **principle-model-the-domain**. If the design crosses a function boundary, run `architect`. Pick the design with the fewest moving parts (**principle-fewest-moving-parts**). Show Jack the shape as the last grilling round, and wait for Jack to confirm the shared understanding before building.
4. Write the throughput checkpoint as four todo items. A dimension that genuinely does not apply keeps its item with `n/a: <reason>`:
   - **Blocking first steps.** Gates run before fan-out.
   - **Independent workstreams.** Disjoint files, services, or layers parallelize. Shared writes serialize.
   - **Shared mutable state.** Default to splitting the target (the **separate-before-serializing-shared-state** principle skill). Serialize only for real invariants.
   - **Smallest safe decomposition.** If one worker is best, name why.
5. Create the branch `feat/<short-desc>` and build. Delegate code-writing to a `jack-agent` with a specific scope (file paths, the named data shape, the existing example to match, the paths of the best-practice and framework skills from step 1, the **ui-build** skill's path and the approved UI plan for anything a user sees, and success criteria). When the implementation admits several valid shapes, delegate through the **arena** skill instead. Comments per **Comments**. Run `deslop` before each commit. Commit as you go with Conventional Commits.
6. For an epic, build it in phases on the same branch. Each phase ends in a verifiable state with its own commits (the **sequence-verifiable-units** principle skill). Do not split it into stacked PRs.
7. Verify on the matching surface with `control-ui` or `control-cli`, against the spec when one exists. Anything a user sees also passes the **ui-verify** skill with an Approve verdict. "Inconclusive" or wrong-surface is not a pass. Flag it.
8. Run **Opening a PR**.

**Reply:** what you built, what you chose and why, the throughput checkpoint, how you verified it, and anything left open. Tables for design alternatives.
